# 发作性睡病单药品小程序功能分析

> 依据两张产品示意图整理，适用于产品需求讨论。图片中的专区名称为“发作性睡病专区”；本文沿用该名称。用户所述“阵发性睡病”与图片名称存在差异，正式命名需确认。图片展示的是概念页面及功能说明，不能据此认定功能已经开发或上线。

## 1. 产品定位与总体结构

这是围绕**单一药品的发作性睡病患者服务小程序**。核心体验是把日常症状与服药记录、疾病管理、药品答疑、就医与支付服务、患者激励集中在一个入口。图片中出现“奥泽悦服药打卡”文案；药品的正式通用名、商品名、适应证及具体服务资格仍需以项目资料确认。

底部导航在四张页面示意中一致，包含：**首页、专病管理、眠宝帮你、权益中心、我的**。图片展示了前四栏的页面内容，未展示“我的”页面。

### 证据标记

- **图示明确**：图片中的页面、标题、入口或旁注直接出现。
- **需求推断**：为使图示功能可用而建议补齐的流程、字段或规则；需产品、医学、法务及业务方确认。

## 3. 首页：每日状态与任务入口

### 3.1 晨起精神状态打卡

**图示明确：** 首页顶部以“今天感觉怎么样？”引导每日记录，四档选项为“精神饱满、有些疲惫、需要小睡、状态不佳”。旁注说明用于快速点选醒后疲惫感。

**建议交互与数据：**

1. 患者当天选择一档状态，记录日期、时间和选项；同一天重复选择时更新当日记录，并给出保存反馈。
2. 首页显示当日完成状态；历史记录可与睡眠日志、用药及 ESS 结果关联查看。
3. 选项是患者主观感受，不应被呈现为诊断结果。若要分析“醒后疲惫感”，需先明确四档对应的量表定义和统计口径。

### 3.2 IP 情感交互头图

**图示明确：** 首页展示“眠宝”羊形象与问候语。旁注提出根据当前服药状态展示动态形象，并附轻量回复。

**建议交互与数据：** 由未打卡、已打卡、临近提醒、漏服记录等状态驱动文案和动画；文案应只做鼓励与任务提示，不暗示疗效或替代医嘱。服药状态的来源与判定规则需确认。

### 3.3 快捷服务

**图示明确：** 首页“快捷服务”区含药房地图、线上购药、随访管家、多元支付，以及不良反应速记入口；右侧有“更多”。图片旁注还提到 AE 上报。

| 功能 | 建议的可用流程与边界（需求推断） |
| --- | --- |
| 药房地图 | 按定位或城市搜索附近药房，展示地址、营业信息和导航；药房数据来源、库存实时性需确认。 |
| 线上购药 | 跳转至合规购药渠道，明确购买资格、处方要求及跳转主体；图片不能证明可在小程序内直接交易。 |
| 随访管家 | 查看随访计划、预约或联系服务人员、接收提醒；服务人员角色与服务时段待确认。 |
| 多元支付 | 进入权益中心的支付与保障服务。 |
| 不良反应速记／AE 上报 | 记录发生时间、表现、严重程度、处理情况及联系方式，并进入核实和上报流程；“速记”与正式 AE 上报是否为同一流程需确认。 |
| 更多 | 承载未放在首屏的服务入口，具体清单待确认。 |

### 3.4 每日双打卡卡片

**图示明确：** “今日任务”包含“奥泽悦今日用药”和“日常小憩时钟”。旁注提出服药时间闹钟、漏服补服指引，以及鼓励 NT1 患者每日小憩两次。示意卡片出现下一次服药倒计时和小憩进度。

**建议交互与数据：**

- **服药打卡**：配置医嘱对应的计划时间，触发提醒，记录计划时间、实际打卡时间、是否漏服及补记原因；在首页显示下一次任务与完成状态。漏服后的具体处理指引应引用经审核的药品资料与医嘱，不能由产品自行生成通用规则。
- **小憩时钟**：设置小憩提醒，开始／暂停／结束计时，记录时长及完成次数；图中建议“15–20 分钟”，如作为产品推荐值，需医学审核并允许按患者方案调整。每日“两次”同样应作为可配置计划，而非对所有患者的固定要求。
- **任务联动**：两类打卡可进入积分与趋势统计。积分规则、补打卡是否计分、跨日规则待确认。

## 4. 发作性睡病专区：症状与睡眠管理

### 4.1 猝倒一键速记与语音病历

**图示明确：** 页面顶部卡片提示“您上一次猝倒是什么时候？”，旁注列出“猝倒一键速记、语音病历”。

**建议交互与数据：** 一键记录发生时间，再补充持续时间、诱因／场景、表现、跌倒或受伤情况、恢复情况及备注；支持语音输入转文字并由用户确认。记录后可查看、修改、删除，并用于周期趋势。若“语音病历”意在形成可分享的就诊摘要，应明确是否包含原始录音、文字转写及医生可见范围。

### 4.2 猝倒周期趋势图

**图示明确：** 专区展示按周一至周日排列的猝倒趋势折线图；图例还出现“猝倒次数”和“诱发情绪分析”。

**建议交互与数据：** 提供周／月切换，按记录日期汇总次数，点按查看对应事件；诱发情绪的输入方式、分类及与事件的关联规则待确认。无记录、补录和数据缺失应分别呈现，避免把“未记录”解释为“没有发作”。

### 4.3 ESS 自测与得分趋势

**图示明确：** 页面有“本周 ESS 得分趋势”柱状图，包含当日得分示意。旁注写明“ESS 自测与得分趋势”。

**建议交互与数据：** 提供 ESS 问卷入口、作答说明、提交与历史结果，按测评日期展示得分变化；明确问卷版本、题目版权／授权、计分规则及解释文案。趋势是自评结果，不直接代表治疗效果或诊断结论。

### 4.4 D2 注意力挑战小游戏

**图示明确：** 专区出现“D2 脑力挑战”卡片；旁注提出升级为“捕捉清醒精灵”互动游戏，追踪脑力集中度变化，并“有时作为复诊客观指标”。

**建议交互与数据：** 设计标准化的游戏时长、操作规则、成绩指标和重复练习机制，记录完成时间与成绩趋势。如确实用于复诊资料，需另行验证指标的可靠性与解释边界；当前图片不足以证明其具有临床评估效力。

### 4.5 睡眠辅助工具

**图示明确：** 页面底部有“小憩闹钟（15–20 分钟）”“睡眠日志（记录睡眠）”“科学贴士（每日知识）”三个入口；旁注另提不良反应上报。

**建议交互与数据：**

- 小憩闹钟与首页任务使用同一套计划和记录，避免重复数据。
- 睡眠日志可记录就寝与起床时间、夜间觉醒、主观睡眠感受及备注；具体字段需依据疾病管理目标确认。
- 科学贴士需有内容来源、审核人、适用人群、发布日期和更新机制。
- 不良反应上报应复用首页入口的同一条记录及处理流程。

## 5. 眠宝帮你：药品信息与医患连接

### 5.1 角色欢迎与智能问答

**图示明确：** 顶部为治疗师形象的“眠宝”IP，气泡文案示例为“我是眠宝 AI，有什么可以帮你？”；下方“智能问答”卡片列出四类入口。旁注称使用“KnowDrug.ai 单药品智能引擎”，并列出语音病历、药品准入查询、用药指导、服药疑惑、不良反应速查、OX2R 新药机制、合理预期引导、PV 识别与上报、患者科普。

| 图中问答入口 | 功能拆解（需求推断） |
| --- | --- |
| 药品使用指导 | 基于经审核资料回答用法、注意事项与常见服药问题；需要资料版本和引用来源。 |
| 猝倒与不良反应速查 | 帮助用户描述症状，提供规范信息与上报入口；无法仅凭对话判断是否属于药品不良反应。 |
| 饮食与药物相互作用 | 根据经过核验的说明书／知识库提供提示；具体药物联用问题应引导咨询医生或药师。 |
| 常见问题解答 | 覆盖疾病、治疗预期、服务流程和权益规则等高频问题。 |

**建议的 AI 对话要求：** 询问意图、展示信息来源与更新时间、保留对话历史、允许反馈答案问题；识别疑似不良反应并引导填写报告；遇到急症、自伤风险或需要调整处方的情况转人工／就医。语音病历、药品准入查询等仅出现在旁注，具体入口及权限待确认。

### 5.2 医患直连服务

**图示明确：** 页面下部展示“复诊预约”“随访专员”“紧急咨询”，旁注另列“就医绿通、添加企微、紧急咨询”。

**建议交互与数据：** 复诊预约需明确医院／医生资源与预约确认；随访专员需说明是否通过企业微信连接；紧急咨询需明确服务时间、响应承诺和紧急情况转诊提示。“就医绿通”的适用资格、服务范围和履约主体待确认。

## 6. 权益中心：支付、积分与社区

### 6.1 多元支付与保障

**图示明确：** 页面列出“商保直付”“惠民保待遇查询”“特定药品福利申请”。旁注扩展为“一码直付、惠民保待遇查询、商保计算器、药品福利申请与报销”。

**建议交互与数据：**

- 商保直付／一码直付：先核验患者、处方、保险与服务资格，再展示可用渠道和支付结果；“一码直付”是否等同于“商保直付”待确认。
- 惠民保待遇查询与商保计算器：输入地区、保单与费用等必要信息，展示估算口径和结果说明；实际报销以保险机构审核为准。
- 特定药品福利申请与报销：展示资格、材料清单、申请进度、审核结果及补件入口；资格与权益规则需业务方提供。

### 6.2 积分商城

**图示明确：** 卡片显示“我的积分”，旁注说明可通过规律打卡、记录量表等行为获得“NT1 战友勋章”和积分，兑换安睡守护包、眠宝抱枕、冥想课程等。

**建议交互与数据：** 积分余额与明细、任务规则、兑换商品、库存与物流／数字内容交付、退款或撤销规则；明确哪些健康行为可获积分及是否有上限。健康行为奖励与药品推广之间的合规边界需专项审核。

### 6.3 眠宝乐园

**图示明确：** “打卡任务”“社区交流”两个入口；旁注提出与眠宝互动、翻牌查看小贴士、扫码加入患者组织。

**建议交互与数据：** 任务页联动首页打卡；互动与翻牌展示经审核的知识内容；社区交流应明确是站内社区、外部群组还是患者组织入口，以及内容审核、隐私与管理责任。扫码加入患者组织的组织主体和授权文案待确认。

## 7. 跨模块用户流程

1. **每日管理**：进入首页 → 晨起状态打卡 → 查看服药／小憩任务 → 完成打卡 → 在专区查看历史趋势 → 依据规则获得积分。
2. **症状记录与复诊**：进入专病管理 → 猝倒速记或语音记录 → 查看周期趋势及 ESS 结果 → 生成或查看复诊资料 → 通过眠宝帮你 页面预约复诊／联系随访。
3. **用药疑问与安全反馈**：从首页或眠宝帮你 发起问题 → 阅读来源明确的答复 → 如涉及疑似不良反应，进入速记／上报 → 人工核实与后续处理。
4. **权益使用**：首页快捷入口或权益中心 → 查询支付与福利资格 → 提交申请／获取渠道 → 查看结果；日常任务积分可在商城兑换。

上述四条流程是依据页面入口组合出的**需求推断**，不是图片已经展示的完整闭环。

## 10. 需要业务方确认的关键问题

1. **疾病和药品命名**：正式病种名称、目标人群（是否仅 NT1）、药品正式名称与适应证是什么？
2. **患者资格**：是否要求实名、处方或确诊信息？家属／照护者是否可使用？
3. **服药规则**：提醒和漏服指引依据哪版获批资料，是否允许按医嘱个性化设置？
4. **医学内容**：ESS 量表版本与授权、D2 游戏用途、科学贴士和 AI 知识库由谁审核？
5. **安全上报**：不良反应速记与正式 PV／AE 上报的责任主体、时限和转接方式是什么？
6. **服务履约**：药房地图、线上购药、就医绿通、随访专员、紧急咨询各由谁提供，覆盖哪些地区？
7. **支付权益**：商保直付、惠民保、福利申请和积分兑换的适用条件与系统对接方是什么？
8. **社区与隐私**：社区是否站内建设，患者组织是否外部运营，敏感信息如何授权、存储和共享？
9. **“我的”页面**：需承载哪些资料、记录、订单、积分、提醒和隐私设置？

## 11. 结论

两张图描述的是以**“记录—观察—答疑—服务—激励”**为主线的单药品患者小程序。其最清晰的功能主轴是每日双打卡、猝倒与 ESS 趋势、药品智能问答，以及支付／随访权益。下一步应先确认药品与患者范围、医学内容、AE 上报责任和服务履约方，再把上述推断流程细化为可开发的页面与接口需求。

### 二级页面通用交互规则

1. 一级页面之间通过底部导航切换；所有二级页面隐藏底部 Tab，并通过顶部返回按钮按访问栈返回上一页。
2. 必填字段在提交前由浏览器校验；跨字段校验由页面处理，例如睡眠日志的时间先后关系。
3. 保存和删除后给出明确提示，列表与统计随本地数据即时更新。
4. 尚未接入真实服务的页面直接说明当前状态，不展示虚构的医生、药房、保险资格或权益结果。
5. 本地原型通过 `localStorage` 保存记录；正式小程序仍需设计账户身份、授权、服务端数据及审计机制。
